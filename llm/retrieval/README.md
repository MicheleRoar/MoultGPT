# `llm/retrieval/` — embedding-based retrieval (RAG)

An alternative / complementary way to pick "which sentences does the LLM
see" to the ontology-gated summarizer already in production
(`pipeline/summarization.py`). See `evaluate_retrieval.py`'s module
docstring for the full reasoning, and `eval_results.md` for an actually-
executed comparison on this repo's own paper corpus (not just a
description of what it would do).

## Why this exists

The production pipeline (`pipeline/domain_pipeline.py`) decides whether a
paper is in-scope and produces one fixed, query-agnostic summary from it.
That's the right tool for gating, but it can't adapt to a specific
question — "what's the moult cycle duration" and "what happens to the
exuviae" get the same context. Retrieval fixes that: embed the paper's
sentences once, then re-rank them fresh for whatever's actually being
asked.

## What's here

- `embedder.py` — two embedding backends: `tfidf` (local, sparse, zero new
  dependencies) and `mistral-embed` (remote, dense, reuses the existing
  `MISTRAL_API_KEY` — no local GPU/weights, consistent with
  `backend/providers.py`'s design).
- `index.py` — a minimal cosine-similarity vector index (not FAISS — see
  that file's docstring for why, and what "outgrowing this" would look
  like).
- `build_index.py` / `retrieve.py` — CLIs to build an index from papers
  (TEI XML or plain text) and query it.
- `evaluate_retrieval.py` — runs the ontology method and both retrieval
  backends on the same real corpus and query set, and writes
  `eval_results.md`.

## Quickstart

```bash
cd llm/retrieval

# Build an index from a few already-parsed papers (no GROBID needed)
python build_index.py --tei ../finetuning/papers/2.tei.xml ../finetuning/papers/3.tei.xml \
    --embedder tfidf --out index/demo_corpus

# Query it
python retrieve.py --index index/demo_corpus --embedder tfidf \
    --query "How many days does the moult cycle last?" --k 5

# Re-run the full comparison (writes eval_results.md)
python evaluate_retrieval.py
```

No new dependencies beyond what's already in `llm/requirements.txt`
(scikit-learn, numpy, requests) for the `tfidf` path. `mistral-embed`
needs `MISTRAL_API_KEY` set — same variable already used for chat
completions.

## Status

Implemented and unit-exercisable end to end with the `tfidf` backend
(`eval_results.md` was generated by actually running this, not written by
hand). The `mistral-embed` backend is implemented but its retrieval
quality is unverified in this environment (no API key available when this
was built) — see `eval_results.md`'s Discussion section for exactly what
that does and doesn't mean.

Not yet wired into the live `/query` endpoint — `pipeline/domain_pipeline.py`
still uses the ontology method exclusively. Swapping in (or blending)
retrieval there is the natural next step once the `mistral-embed` path has
been validated with a real key.
